# Branch Sync Agent V2 — Web 分支维护平台需求文档

> 版本：v0.1（需求初稿）
> 日期：2026-08-24
> 状态：待评审

## 一、背景

Branch Sync Agent V1 已交付：每日检测 RCIOS 代码库分支合入的 bug-fix commit，判定是否需要同步，在独立 worktree 中完成 cherry-pick、冲突解决、多型号编译验证、生成 diff-patch，并发送 HTML 报告邮件（真实送达已确认）。

V1 的**能力边界（硬约束）**：Agent 永不推送分支。同步产物（patch + worktree）交由人工应用。V1 的维护人员收到邮件后，需**手动登录服务器、进入 worktree、执行 git push**——操作繁琐且无法集中查看历史。

V2 目标：提供一个 **Web 分支维护平台**，让维护人员**通过浏览器**查看报告、审阅 patch、**人工触发推送**，将"手动 SSH 操作"升级为"网页操作"，同时保留能力边界（推送由人工触发，Agent 不自动推）。

## 二、目标

1. 维护人员通过浏览器登录平台，集中查看每日分支同步报告与历史。
2. 在平台界面审阅各分支的同步结果（patch / diff / 编译状态）。
3. 在平台界面**人工触发推送**（把 V1 worktree 中的 cherry-pick 结果推到远程目标分支）。
4. 平台默认展示前一天内容，每日刷新。
5. 保留能力边界：推送动作由人触发，Agent 永不自动推送。

## 三、用户角色

| 角色 | 权限 | 说明 |
|---|---|---|
| **查看者** | 登录后可查看报告、patch、历史记录 | 只读，不可执行推送 |
| **操作者** | 查看者权限 + 可执行推送 | 负责实际推送维护人员（默认收件人） |
| **管理员**（可选，后续） | 操作者权限 + 用户管理/配置 | V2 初版可不含，预留 |

> 初版建议：统一登录（公司内部工具），所有登录用户默认"操作者"。角色细分作为扩展项。

## 四、核心功能需求

### FR1：用户认证与登录

- 用户通过浏览器访问平台 URL，使用公司统一认证（如 LDAP / SSO）登录。
- 未登录用户无法访问任何页面。
- 登录后会话保持（可配置过期时间）。
- 退出登录。

### FR2：报告展示（核心）

- 平台首页展示**前一天的维护报告**（默认保存前一天内容，每日刷新）。
- 报告内容与 V1 HTML 邮件报告一致，含三区块：
  - **Action Required**：需人工处理的项（停批分支、未修复 commit、ManualReview、forbidden_paths 命中、推送建议）。
  - **已成功同步**：各分支 cherry-pick / 冲突解决 / 编译 / patch 结果。
  - **检测信息**：扫描窗口、分支数、commit 数、四态结论明细、无需同步的 commit 及理由。
- 每个 commit / 分支可**展开查看详情**：patch 内容、diff、Agent 修复记录、编译日志摘要。
- 支持**按日期查看历史报告**（下拉或日历选择）。
- 支持**按结论筛选**（NeedSync / AlreadyIncluded / ManualReview / OutOfScope / 失败 / 停批）。

### FR3：推送操作（核心，人工触发）

- 对**已成功同步的分支**（worktree 中 cherry-pick + 编译验证通过），平台展示**可推送状态**与**推送命令建议**。
- 操作者点击"推送"按钮后：
  - 平台显示确认对话框（展示目标分支、commit 范围、patch 摘要）。
  - 操作者确认后，平台**在对应 worktree 中执行推送**（`git push origin <target_branch>`）。
  - 推送动作由**人工触发**，Agent 不自动执行。
- 推送结果回显（成功 / 失败 + 错误信息），并记录操作日志。
- **仅允许推送"已成功同步且编译通过"的分支**；失败 / 停批 / ManualReview 分支不可推送（显示锁定原因）。

### FR4：操作日志与审计

- 平台记录所有操作（登录、查看、推送、导出）：
  - 时间、操作人、目标分支、commit 范围、结果。
- 推送操作必须留痕，供审计（对应闸门 4 事后审核 + 闸门 5 审计）。

### FR5：历史与数据保留

- 平台**默认保存前一天内容**（即报告数据按周期保留，默认保留 N 天可配置）。
- 每日刷新：新周期报告生成后，平台自动更新首页展示。
- 数据来源：V1 的 SQLite（周期记录、报告、decisions.json）+ worktree（保留现场）。

### FR6：导出（可选）

- 支持导出报告 / patch / 操作日志（HTML / 文本）。
- 初版可不含，预留接口。

## 五、非功能需求

### NFR1：能力边界（硬约束）
- **Agent 永不推送**：推送必须由人工在平台触发。平台后端不得有任何自动推送逻辑。
- 平台推送仅在"已成功同步且编译通过"分支上可用（对应 V1 安全闸门）。

### NFR2：安全
- 认证：公司统一认证（LDAP/SSO），初版可简化。
- 授权：查看者/操作者角色（初版可统一为操作者）。
- 推送操作二次确认，防误触。
- 敏感操作留痕（FR4）。

### NFR3：性能
- 并发访问：内部工具，低并发（10 用户内即可）。
- 报告加载：首页 < 3 秒；大报告（多分支）分页或懒加载。

### NFR4：可靠性
- 平台崩溃不影响 V1 Agent 周期运行（平台只读 SQLite + worktree，不写 Agent 状态）。
- 推送失败有明确错误提示，可重试。

### NFR5：可维护性
- 技术栈与 V1 一致（Python），便于维护。
- 配置走环境变量（与 V1 一致，不硬编码路径/密钥）。

## 六、技术约束与建议

- **后端**：Python（与 V1 一致）。建议 FastAPI（轻量、异步、适合内部工具）。
- **前端**：简单服务端渲染（Jinja2 模板 + 少量 JS）或轻量 SPA（Vue/React）。初版建议服务端渲染为主，减少复杂度。
- **数据**：读 V1 的 SQLite（`logs/state.sqlite3` + 周期目录）；worktree 路径从 SQLite/周期记录读取。
- **部署**：平台与 V1 Agent 同服务器；平台进程独立（不阻塞 Agent cron）。
- **推送执行**：平台后端在 worktree 中执行 `git push`（通过受限命令执行器，仅白名单 `push` 到已确认目标分支）；或**仅生成推送命令供操作者复制执行**（最保守）。初版建议：生成命令 + 平台执行可选。

## 七、页面结构（初版）

```
登录页
  └─ 首页（报告总览）
       ├─ 日期选择 / 报告列表
       ├─ Action Required 区块（含推送建议）
       ├─ 已成功同步区块（每分支：状态、可推送、推送按钮）
       ├─ 检测信息区块（四态明细）
       └─ 提交/分支详情（patch、diff、编译日志）
  ├─ 历史报告页
  ├─ 操作日志页
  └─ 设置（角色/保留天数，可选）
```

## 八、验收标准

1. 维护人员通过浏览器登录，能看到前一天的维护报告。
2. 报告含三区块，展开能看 patch / diff / 编译日志。
3. 对已成功同步分支，操作者可点击推送，确认后执行，结果回显。
4. 失败 / 停批 / ManualReview 分支不可推送，显示原因。
5. 推送操作在日志中留痕（操作人、时间、分支、结果）。
6. Agent 无任何自动推送逻辑（代码审查确认）。
7. 平台每日刷新，默认保留前一天内容。

## 九、边界（V2 不做）

- 不实现自动推送（能力边际，硬约束）。
- 不实现 Agent 的冲突/编译自动修复（那是 V1 的 Agent 职责，平台只展示）。
- 不做多仓库管理（V1 单 repo，V2 保持）。
- 不做复杂的用户管理系统（初版统一登录，角色细分后续）。

## 十、待确认项

- 认证方式：LDAP / SSO / 简单账号？（初版建议先公司认证）
- 推送执行：平台直接执行 `git push` 还是仅生成命令供人工复制？（默认：平台执行 + 二次确认）
- 数据保留天数：默认前一天，保留多少天？（默认 30 天可配置）
- 部署形态：平台与 Agent 同机，独立进程 + 反向代理？（默认同机 systemd + nginx）
