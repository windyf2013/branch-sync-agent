# Branch Sync Agent V2 — Web 分支维护工作台需求文档

> 版本：v0.3（整体方案与细节决策后修订）
> 日期：2026-08-24
> 状态：待评审
> 说明：本版吸收"超期即弃"原则，重构首页定义、推送链路、并发模型与对接方式；按**商用交付标准**要求安全、可靠性、可运维性。

## 一、背景与定位

Branch Sync Agent V1 已交付：每日检测 RCIOS 代码库分支合入的 bug-fix commit，判定是否需要同步，在独立 worktree 中完成 cherry-pick、冲突解决、多型号编译验证、生成 diff-patch，并发送 HTML 报告邮件（真实送达已确认）。

**V2 定位：完整的分支维护工作台。** 邮件只是"通知入口"（告诉用户有新报告/新操作），**平台才是日常操作的地方**——用户在这里查看、审阅、决策、执行合入同步与推送操作。

能力边界（硬约束，贯穿 V1/V2）：**Agent 永不推送分支**。V2 中推送由"人"在平台上触发（确认后平台代执行），Agent 不自动推、平台不自动推。

## 二、总体方案（框架已定）

### 2.1 超期即弃原则（核心设计决策）

- 同步结果（worktree 现场）只在**一个周期**内有操作价值：远端会在周期推进时产生新合入，超期重放旧 patch 必然冲突或重复合入。
- 因此：**worktree 只保留当前周期**，由 V1 cron 开跑时清理（V1 `cleanup_worktrees` 现有行为不变）。
- 超期分支**不做续做/推送**，只提供**只读查看**与**重新同步**（`bsa rerun --fresh`，基于当前远端重做）。
- **不存在"用 patch 重建旧现场"的机制**。旧 base 重放被明确排除。

### 2.2 生命周期

| 分支状态 | 可操作项 |
|---|---|
| **活 worktree（当前周期）** | 查看 / 人工 SSH 处理 / 续做（`rerun` 保留现场）/ 推送（仅 SUCCESS） |
| **超期分支** | 只读查看（patch/日志/历史）+ 重新同步（`rerun --fresh`） |

### 2.3 并发模型

- 全局 `flock` 串行化所有 V1 执行：cron `run-cycle`、平台触发的 `sync/rerun`、worktree 清理。V1 本就低频（日一次 + 偶尔手动），串行可接受。
- 平台触发的任务使用**独立 cycle_id 命名空间**（如 `manual-*`），不与每日周期 checkpoint 冲突。

### 2.4 对接方式（方案 B，独立进程）

- 平台独立进程，与 Agent 解耦；平台崩溃不影响 Agent cron 运行。
- **读**：V1 投影 CLI（`bsa report <cycle> --json`）输出结构化状态，平台只消费 JSON，不解析 LangGraph checkpoint 内部结构。
- **写**：平台对 V1 的一切写入只经 V1 CLI 子进程（`bsa sync/rerun/override`），绝不直接写 V1 的库。
- **数据关联**：平台本地库用 V1 标识符（`cycle_id / target_branch / sha / patch_path / worktree_path`）逻辑关联 V1 数据；渲染时聚合"V1 状态 + 平台活动"，形成完整视图（如分支详情页 = V1 同步状态 + 平台推送/处理记录）。V1 数据不自成孤岛。

### 2.5 实时性

- 平台页面**实时读状态，不缓存**。长闲置后操作前自动刷新（每次请求从 V1 投影读取最新状态）。

## 三、用户角色

| 角色 | 权限 | 说明 |
|---|---|---|
| **查看者** | 查看报告、patch、日志、历史、实时状态 | 只读，不可执行操作 |
| **操作者** | 查看者权限 + 触发同步 / 重跑 / 处理人工项 / 推送 | 日常维护执行者；**推送与敏感操作校验操作者角色** |

> 初版即分两角色（登录后按配置分配），不做审批链。

## 四、核心功能需求

### FR1：用户认证与登录
- 浏览器访问平台 URL，登录后使用。
- **初版认证：简单账号过渡**（环境变量配置账号/密码，表单认证 + CSRF），认证层抽接口；公司 LDAP/SSO 就绪后切换实现，不改其余逻辑。
- 未登录不可访问；会话保持（过期可配，默认 8h + 闲置超时自动失效）。
- 退出登录；会话 cookie 采用 HttpOnly + Secure + SameSite=Lax。

### FR2：工作台首页（实时）+ 历史报告页
- **首页 = 实时工作台**（不再展示"前一天报告"）：
  - **待办区**：可推送列表（当前周期 SUCCESS 分支 + 推送按钮）、ManualReview 待确认、失败/停批重跑入口。
  - **当前周期实时总览**：各 target 分支状态徽章（可手动/自动刷新）。
  - **快速操作**：触发同步（源+目标 / `--sha`）、重跑。
  - **历史报告入口**：按日期只读查看历史报告。
- **历史报告页**：按日期查看历史周期报告（原 FR2 的"前一天报告"降级为此），三区块视图（Action Required / 已成功同步 / 检测信息），按结论筛选。
- 每个 commit/分支可展开查看详情：patch、diff、编译日志、Agent 修复记录（**详情独立路由页面，patch/日志按需加载**）。

### FR3：手动触发同步
- **默认操作：源分支 + 目标分支**，平台走完整链路：检测该源分支最近窗口 commit → 对目标重判结论 → 只同步 NeedSync。
- **兼容操作：指定 commit SHA 直同步**（用户可能只想同步某个问题）：`bsa sync <target> --sha <sha>`，跳过决策直接同步；后续 cherry-pick→build→patch 仍走五道闸门（白名单/编译验证/审计），与"确认继续"语义一致，不破安全模型。
- **重跑**：失败分支可重跑（`bsa rerun <target>`，见 FR4）。
- 同步流程**异步执行**：发起后展示进度（任务状态机 queued→running→succeeded/failed，轮询查询），完成后结果回到平台。

### FR4：处理人工项
- **查看失败现场**：停批/失败分支的冲突现场、编译错误、Agent 修复记录（来自投影 JSON 与日志文件）。
- **人工介入决策**：
  - **改判定**（某 commit 的 is_bug_fix / risk）：平台写 V1 `judgments.json`（V1 已有"人工覆盖优先"钩子），改完重跑该 commit 决策。
  - **确认允许同步**（ManualReview 项）：复用直同步路径（`bsa sync <target> --sha <sha>`）强制执行。
  - **重跑**：`bsa rerun <target>`（沿用当前活 worktree，按 git 状态重入）或 `--fresh`（重建重同步）。
  - **放弃**：标记该 commit/分支放弃，记录操作日志。

### FR5：推送操作（能力边界落地）
- 仅**当前周期活 worktree 且状态 SUCCESS**（全部 cherry-pick + 全部 required_models 编译通过）的分支显示可推送状态。
- **严格四道闸**校验（任一不过即拒绝并显示原因）：
  1. 状态 = SUCCESS；
  2. worktree 存在；
  3. 目标分支不在 `safety_rules.yaml` 的 `forbidden_branches`（如 master）；
  4. `git status --porcelain` 干净（防把未提交改动一起推上去）。
- 操作者点"推送" → 平台显示确认框（目标分支、commit 范围、patch 摘要）→ 确认后平台在对应 worktree 执行 **`git push origin HEAD:<target>`**。
  - worktree 为 detached HEAD，故用 `HEAD:<target>` 而非 `git push origin <分支>`。
  - **绝不加 `--force`**（硬约束）：远端已前进时 git 默认拒绝非 fast-forward，干净失败。
- 推送由**人工触发**，Agent 不自动推；平台是执行器，不是决策者。
- 失败/停批/ManualReview 分支不可推送（显示锁定原因）。
- 推送结果回显（成功/失败+错误）；失败提示"远端已前进请重新同步"。
- 推送记录操作日志（操作人、时间、分支、commit 范围、结果）。

### FR6：操作日志与审计
- 记录敏感操作：登录/登出、触发同步、重跑、改判定、确认继续、推送、放弃。
- **推送必须留痕**（操作人、时间、分支、commit 范围、结果）——对应闸门 4 事后审核 + 闸门 5 审计。
- 审计类数据**永久保留**（见 FR7 分级）。

### FR7：数据保留（分级）
- **L1 审计（永久）**：cycle.json / decisions.json / report.html / audit·diff / patch / 推送与操作日志。
- **L2 体积日志（默认 30 天，可配置，每日清理）**：build log / run.log。
- **L3 现场（仅当前周期）**：worktree，由 V1 cron 清理。
- 数据来源：V1 SQLite（checkpoint）+ 周期目录 + worktree；平台经投影 CLI 读取。

### FR8：导出（可选）
- 导出报告/patch/操作日志。初版可不含，预留接口。

## 五、非功能需求

### NFR1：能力边界（硬约束）
- **Agent/平台永不自动推送**。推送必须由人工触发。
- 平台推送仅在"当前周期活 worktree + SUCCESS + 四道闸通过"上可用。
- **推送禁止 `--force`**。
- 代码审查确认：平台无任何自动推送逻辑。

### NFR2：安全（商用交付基线）
- 认证：初版简单账号过渡（env 配置），接口化，后续接 LDAP/SSO。
- 授权：查看者/操作者两角色；**每个端点校验角色**（不依赖藏按钮）。
- 推送二次确认（确认框 + 结果回显）。
- CSRF：表单 POST 全走 token。
- 会话：HttpOnly + Secure + SameSite=Lax；过期可配。
- 登录防爆破：nginx `limit_req` 限速登录路径。
- HTTPS 强制：nginx http→https 跳转，TLS 终结于 nginx。
- 密钥只走环境变量，日志脱敏。

### NFR3：性能
- 低并发（10 用户内）；首页 < 3 秒；详情独立路由，patch/编译日志按需加载。

### NFR4：可靠性
- 平台崩溃不影响 V1 Agent cron 运行。
- 异步同步任务可查询进度/结果；子进程超时兜底、退出后清理（无僵尸）。
- 同一 target 并发触发直接拒绝（"已在运行"）。
- 全局 `flock` 串行化所有 V1 执行（cron / 平台触发 / 清理）。
- V1 `state.sqlite3` 开 WAL + busy_timeout，平台投影读取不撞写锁。
- 推送失败有明确错误，可重试（重试 = 重新同步）。

### NFR5：可维护性
- 技术栈与 V1 一致（Python FastAPI + Jinja2 SSR + 少量 JS）。
- 配置走环境变量，不硬编码。
- 平台 DB 带 `schema_version` 做迁移。

### NFR6：备份与恢复
- 每日备份：平台 DB + V1 `state.sqlite3` + `judgments.json` / `cycle.json`（同机保留 N 份）。
- worktree 不纳入备份（可重建/重同步）。
- 恢复 = 还原备份 + 重建环境 + 重跑同步。

### NFR7：可观测性
- 平台健康检查端点（systemd/nginx 探活）。
- 结构化请求日志 + logrotate。
- V1 周期失败（含 cron）在工作台有醒目标记。

## 六、技术约束与对接

- **后端**：Python FastAPI（轻量、异步）。
- **前端**：服务端渲染（Jinja2 + 少量 JS）为主，详情独立路由，任务进度轮询。
- **数据**：平台只读 V1 数据（经投影 CLI），写入经 V1 CLI 子进程；平台自有库独立 SQLite（会话、操作日志、任务注册表），用 V1 标识符逻辑关联。
- **与 V1 对接**：
  - 投影：`bsa report <cycle> --json` 输出结构化状态。
  - 同步：`bsa sync <src> <target> [--sha ...]`。
  - 重跑：`bsa rerun <target> [--cycle <id>] [--fresh]`。
  - 改判定：`bsa override <sha> [--is-bug-fix] [--risk]`。
  - 推送：平台后端在对应 worktree 执行 `git push origin HEAD:<target>`（受限执行器，仅白名单 push 到已确认目标分支，禁 `--force`）。
  - 并发：全局 `flock`。
- **部署**：平台与 Agent 同机，独立进程 + systemd + nginx 反代（TLS 终结）+ 环境变量配置。

## 七、页面结构

```
登录页
  └─ 工作台首页（实时）
       ├─ 待办区（可推送 / ManualReview 待确认 / 失败停批重跑）
       ├─ 当前周期实时总览（各 target 状态徽章，可刷新）
       ├─ 快速操作（触发同步 源+目标 / --sha，重跑）
       ├─ 分支详情页（patch/diff/编译日志/Agent 修复记录/平台活动聚合）
       └─ Agent 状态（V1 周期失败醒目标记）
  ├─ 历史报告页（按日期，三区块只读）
  ├─ 操作日志页（审计）
  └─ 设置（角色分配 / 保留天数 / 会话过期，可选）
```

## 八、V1 新增改动清单（框架引出的硬改动）

| 类别 | 改动 |
|---|---|
| CLI | 新增 `bsa sync <src> <target> [--sha ...]`、`bsa rerun <target> [--cycle] [--fresh]`、`bsa override <sha>`、`bsa report <cycle> --json` |
| 执行 | 全局 `flock` 锁；分支级重入子图（单 target 同步/重跑）；手动任务独立 cycle_id 命名空间 |
| 续跑语义 | `rerun` 默认沿用当前活 worktree、按 git 状态重入（未完成 cherry-pick 继续、已应用跳过）、全量 build 验证后更新 patch；`--fresh` 重建并先重判结论（若 AlreadyIncluded/OutOfScope 则停止提示） |
| 数据 | 平台写 `judgments.json`（已有钩子）；`state.sqlite3` 开 WAL |
| 推送 | 平台受限执行器白名单 `push`（仅 `origin HEAD:<target>`，禁 `--force`） |

## 九、验收标准

1. 查看者登录可读、不可操作；操作者登录可触发同步/重跑/改判定/推送。
2. 首页为实时工作台：当前周期分支状态、待办区（可推送/ManualReview/失败停批）、快速操作入口。
3. 可主动发起同步（选源+目标，或指定 `--sha`），进度/结果回到平台。
4. 可重跑失败分支（保留现场续跑 / `--fresh` 重同步）；可处理 ManualReview（改判定/确认继续/重跑/放弃）。
5. 对当前周期 SUCCESS 分支，操作者点推送→四道闸校验→确认框→平台执行→结果回显；失败显示原因并可重同步。
6. 超期分支无推送/续做入口，仅只读查看 + 重新同步。
7. 推送/操作在日志留痕（永久），审计可查。
8. Agent 与平台均无自动推送逻辑、推送无 `--force`（代码审查确认）。
9. 平台崩溃不影响 V1 cron 运行；并发触发被全局锁与"已在运行"拒绝。
10. 数据分级保留（L1 永久 / L2 30 天可配 / L3 仅当前周期）。

## 十、边界（V2 不做）

- 不自动推送（能力边际，硬约束）。
- 不做"旧现场重建/重放"（超期即弃，重新同步）。
- 不实现 Agent 的冲突/编译自动修复（V1 职责，平台只展示/触发）。
- 不做审批链（角色细分已含查看者/操作者，审批链为扩展项）。
- 不做多仓库管理（V1 单 repo，V2 保持）。
- 不提供平台内文件编辑（人工处理走 SSH 改活 worktree）。

## 十一、待确认项（剩余开放）

- 认证：简单账号过渡的账号管理方式（env 静态 vs 平台内可管理）；LDAP/SSO 切换时机。
- 日志保留天数具体值（默认 30 天）。
- 备份保留份数与介质（同机目录 vs 外部存储）。
- 会话过期具体默认值（默认 8h + 闲置超时）。
