# Branch Sync Agent V2 — Web 分支维护工作台需求文档

> 版本：v0.2（需求评审后修订）
> 日期：2026-08-24
> 状态：待评审

## 一、背景与定位

Branch Sync Agent V1 已交付：每日检测 RCIOS 代码库分支合入的 bug-fix commit，判定是否需要同步，在独立 worktree 中完成 cherry-pick、冲突解决、多型号编译验证、生成 diff-patch，并发送 HTML 报告邮件（真实送达已确认）。

**V2 定位：完整的分支维护工作台。** 邮件只是"通知入口"（告诉用户有新报告/新操作），**平台才是日常操作的地方**——用户在这里集中查看、审阅、决策、执行合入同步操作。

能力边界（硬约束，贯穿 V1/V2）：**Agent 永不推送分支**。V2 中推送由"人"在平台上触发（确认后平台代执行），Agent 不自动推、平台不自动推。

## 二、目标

1. 维护人员通过浏览器登录工作台，集中查看每日报告、历史、patch、编译日志。
2. 在工作台对需要同步的分支**执行合入同步操作**（触发同步、处理人工项、推送）。
3. 将 V1 的"邮件 + 手动 SSH 操作"升级为"邮件通知 + 网页操作台"。
4. 保留能力边界：推送由人触发，Agent/平台不自动推送。

## 三、用户角色

| 角色 | 权限 | 说明 |
|---|---|---|
| **查看者** | 查看报告、patch、日志、历史 | 只读，不可执行操作 |
| **操作者** | 查看者权限 + 触发同步 / 处理人工项 / 推送 | 日常维护执行者 |

> 初版：统一登录，默认所有登录用户为"操作者"。角色细分（管理员、审批链）作为扩展项。

## 四、核心功能需求（四类操作，全都要）

### FR1：用户认证与登录
- 浏览器访问平台 URL，公司统一认证登录（LDAP/SSO）。
- 未登录不可访问；会话保持（可配置过期）。
- 退出登录。

### FR2：查看与审计（基础功能）
- 首页展示**前一天报告**（默认保存前一天内容，每日刷新）。
- 报告三区块：Action Required / 已成功同步 / 检测信息。
- 每个 commit/分支可展开查看详情：patch、diff、编译日志、Agent 修复记录。
- 按日期查看历史报告；按结论筛选（NeedSync/AlreadyIncluded/ManualReview/OutOfScope/失败/停批）。
- 操作历史日志（谁、何时、对哪个分支做了什么）。

### FR3：手动触发同步
- 用户可**主动发起**一次 Agent 同步流程：选定"源分支 + 目标分支"（或某需同步的 commit），平台调起 Agent 执行 检测→cherry-pick→编译→patch，结果回到平台展示。
- 用户可**重跑**失败的同步（人工修完现场后，对失败分支重跑）。
- 同步流程异步执行：发起后展示进度，完成后结果回到平台。

### FR4：处理人工项
- **查看失败现场**：停批/失败分支的冲突现场、编译错误、Agent 修复记录。
- **人工介入决策**：
  - 修改某 commit 的 is_bug_fix / risk 判定（对应 V1 人工覆盖 judgments），重跑决策。
  - 确认"允许同步"后继续执行（ManualReview 项）。
  - 重跑 / 放弃 / 手动修后继续。

### FR5：推送操作（能力边界落地）
- 仅对**已成功同步且编译通过**的分支显示可推送状态。
- 操作者点"推送" → 平台显示确认框（目标分支、commit 范围、patch 摘要）→ 确认后**平台在对应 worktree 执行 `git push origin <分支>`**。
- 推送由**人工触发**，Agent 不自动推；平台是执行器，不是决策者。
- 失败/停批/ManualReview 分支不可推送（显示锁定原因）。
- 推送结果回显（成功/失败+错误），记录操作日志。

### FR6：操作日志与审计
- 记录所有操作：登录、查看、触发同步、处理人工项、推送。
- 推送必须留痕（操作人、时间、分支、commit 范围、结果）——对应闸门 4 事后审核 + 闸门 5 审计。

### FR7：数据保留
- 平台默认保存前一天内容，每日刷新（报告数据按周期保留，默认保留天数可配置）。
- 数据来源：V1 SQLite（周期记录/报告/decisions.json）+ worktree（现场）。

### FR8：导出（可选）
- 导出报告/patch/操作日志。初版可不含，预留接口。

## 五、非功能需求

### NFR1：能力边界（硬约束）
- **Agent/平台永不自动推送**。推送必须由人工触发。
- 平台推送仅在"已成功同步且编译通过"分支上可用。
- 代码审查确认：平台无任何自动推送逻辑。

### NFR2：安全
- 认证：公司统一认证（LDAP/SSO）。
- 授权：查看者/操作者。
- 推送二次确认。
- 敏感操作留痕。

### NFR3：性能
- 低并发（10 用户内）；首页 < 3 秒；大报告分页/懒加载。

### NFR4：可靠性
- 平台崩溃不影响 V1 Agent 周期运行。
- 异步同步任务可查询进度/结果。
- 推送失败有明确错误，可重试。

### NFR5：可维护性
- 技术栈与 V1 一致（Python）；配置走环境变量，不硬编码。

## 六、技术约束与对接

- **后端**：Python FastAPI（轻量、异步、适合内部工具）。
- **前端**：服务端渲染（Jinja2 + 少量 JS）为主，减少复杂度。
- **数据**：平台**只读** V1 SQLite（`logs/state.sqlite3` + 周期目录）；worktree 路径从 SQLite/周期记录读取。
- **与 V1 对接（方案 B，独立进程）**：
  - 平台是独立进程，与 Agent 解耦。
  - 触发同步 / 重跑：平台后端通过**子进程调用 V1 CLI**（`bsa run-cycle` / 新增 CLI 命令），Agent 执行结果写回 SQLite，平台读取展示。
  - 推送：平台后端在对应 worktree 执行 `git push`（受限执行器，仅白名单 `push` 到已确认目标分支）。
  - 平台崩溃不影响 Agent cron 运行。
- **部署**：平台与 Agent 同机，独立进程 + 反向代理（nginx/systemd）。

## 七、页面结构

```
登录页
  └─ 工作台首页（前一天报告）
       ├─ Action Required（含人工项处理入口）
       ├─ 已成功同步（可推送分支：推送按钮）
       ├─ 检测信息（四态明细）
       ├─ 提交/分支详情（patch/diff/编译日志/Agent修复记录）
       ├─ 触发同步（选择源+目标分支发起）
       └─ 人工项处理（改判定/确认继续/重跑/放弃）
  ├─ 历史报告页（按日期）
  ├─ 操作日志页（审计）
  └─ 设置（角色/保留天数，可选）
```

## 八、验收标准

1. 维护人员浏览器登录，看到前一天的维护报告（三区块）。
2. 展开可查看 patch/diff/编译日志/Agent 修复记录。
3. 可主动发起同步（选源+目标分支），进度/结果回到平台。
4. 可重跑失败分支；可处理 ManualReview（改判定/确认/重跑/放弃）。
5. 对已成功同步分支，操作者点推送→确认→平台执行→结果回显。
6. 失败/停批/ManualReview 分支不可推送，显示原因。
7. 推送/操作在日志留痕。
8. Agent 与平台均无自动推送逻辑（代码审查确认）。
9. 平台每日刷新，默认保留前一天内容。

## 九、边界（V2 不做）

- 不自动推送（能力边际，硬约束）。
- 不实现 Agent 的冲突/编译自动修复（那是 V1 Agent 职责，平台只展示/触发）。
- 不做多仓库管理（V1 单 repo，V2 保持）。
- 不做复杂用户管理/审批链（初版统一登录，扩展项）。

## 十、待确认项（后续细化）

- 认证：LDAP / SSO / 简单账号（初版建议先公司认证）。
- 数据保留天数（默认前一天，保留 30 天可配置）。
- 前端形态：纯服务端渲染 vs 轻量 SPA（初版建议服务端渲染）。
- 触发同步的 CLI 命令：新增 `bsa sync <源> <目标>` / `bsa rerun <分支>` 等。
