# 分支管理规范

本文档定义代码仓库的分支类型、命名规则、需求追溯与权限分配，适用于产品开发与维护过程中的版本管理。

> **核心原则：** 分支名通过「分支前缀」机制自然编码父子从属关系，确保任意时刻可追溯到父分支。

---

## 1. 分支类型概览

| 分支类型     | 用途                     | 基于分支              |
| -------- | ---------------------- | ----------------- |
| Master   | 主分支，存放稳定发布版本           | —                 |
| Develop  | 集成开发分支，多款产品并行开发        | Master            |
| Feature  | 新增特性与需求开发              | Develop           |
| Release  | 产品 TR5 至 GA 阶段的 BUG 修复 | Develop           |
| Fix      | 已发布产品的生命周期维护           | Release           |
| Personal | 个人日常开发与调测              | Develop / Release |

---

## 2. Master 分支

主分支，用于存放经过验证、可对外发布的稳定代码。

---

## 3. Develop 分支

集成开发分支，多款产品在此并行开发。

### 3.1 命名规范

```
br_版本号_develop_用途_日期
```

- **用途**：本分支的开发对象或开发产品，如 `cmcc`、`msg`、`fttr`（政企网关）、`sdwan`；基线产品可省略用途字段。
- **日期**：格式为 `YYYYMMDD`。

**示例：**

```
br_v4.10_develop_msg_20200405
br_v4.10_develop_wifi6_20200405
br_v4.34_develop_FTTR_P300_CTEB_20260316
```

### 3.2 分支前缀约定

Develop 分支的命名自动构成其所有后代分支的 **「分支前缀」**（branch prefix）。

> **分支前缀** = Develop 分支名去掉末尾 `_YYYYMMDD` 日期段。

示例：`br_v4.34_develop_FTTR_P300_CTEB_20260316` 的分支前缀为 `br_v4.34_develop_FTTR_P300_CTEB`。

所有基于此 Develop 拉取的 Feature / Release 分支，**必须**以该前缀作为命名开头，从而自然编码父子从属关系（见 [[#4.1 命名规范|Feature 命名]]）。

### 3.3 子 Develop 分支的家族关系标注

当新的 Develop 分支**不是从 Master 拉出，而是从既有 Develop 分支拉出**时，名称上的「分支前缀」不足以表达 Develop → Develop 的父子关系（前缀机制仅覆盖 Develop → Feature/Release/Personal）。

此时使用 `git notes` 在子 Develop 分支的**首个 commit** 上显式标注父分支名：

```bash
# 1. 从父 Develop 拉出新 Develop
git checkout -b br_v4.34_develop_FTTR_P300_CTEB_20260316 br_v4.10_develop_msg_20200405

# 2. 标注父子关系（在新分支的首个 commit 上）
git notes add -m "parent: br_v4.10_develop_msg_20200405" HEAD
```

> **约定：** `parent:` 后的值为父 Develop 分支的完整名称，不含 `origin/` 前缀。

**工具解析顺序：** 家族树工具（`git-branch-family.sh`）在追溯 Develop 分支的来源时，优先读取 `git notes` 中的 `parent:` 标注；若未标注，则回退到 `git merge-base` 从 git DAG 中推断。

### 3.4 权限

| 角色             | 权限                   |
| -------------- | -------------------- |
| SSE、领域 SE、项目经理 | 读写、归并                |
| 开发人员           | 只读；可拉取分支，可 push 个人分支 |

---

## 4. Feature 分支

产品开发或维护过程中，用于新增特性与需求开发，基于 Develop 分支拉取。

### 4.1 命名规范

Feature 分支名**必须以父 Develop 分支的分支前缀开头**，确保从属关系可自动解析。

```
{Develop前缀}_feature_{特性名称}_{日期}
```

| 字段 | 说明 | 示例 |
|------|------|------|
| `{Develop前缀}` | 父 Develop 分支去掉末尾日期（见 [[#3.2 分支前缀约定\|分支前缀约定]]） | `br_v4.10_develop_msg` |
| `{特性名称}` | 特性简短标识 | `dhcp`、`netconf`、`safe` |
| `{日期}` | 分支创建日期 `YYYYMMDD` | `20200405` |

> **要求：** 特性名称应控制在 1–3 个英文词以内，使用小写 + 下划线分隔。禁止使用个人姓名或昵称。

**示例：**

```
br_v4.10_develop_msg_feature_dhcp_20200405
br_v4.10_develop_msg_feature_netconf_20200405
br_v4.34_develop_FTTR_P300_CTEB_feature_nfc_20260408
br_v4.34_develop_FTTR_P300_CTEB_feature_safe_20260507
```

### 4.2 权限

| 角色     | 权限  |
| ------ | --- |
| 所有开发人员 | 读写  |

---

## 5. Release 分支

Develop 分支上并行着多款产品的开发。为保证某款产品的稳定性，当该产品进入 **TR5** 后，基于 Develop 分支拉取 Release 分支，用于 **TR5 ~ GA** 之间的 BUG 修复。

### 5.1 命名规范

Release 分支名**必须以父 Develop 分支的分支前缀开头**。

```
{Develop前缀}_release_{版本标记}_{日期}
```

| 字段            | 说明                           |
| ------------- | ---------------------------- |
| `{Develop前缀}` | 父 Develop 分支去掉末尾日期           |
| `{版本标记}`      | 发布里程碑标识，如 `p360`、`p370`、`GA` |
| `{日期}`        | 分支创建日期 `YYYYMMDD`            |

**示例：**

```
br_v4.10_develop_msg_release_p360_20200405
br_v4.10_develop_msg_release_p370_20200405
br_v4.10_develop_wifi6_release_20200405
br_v4.10_develop_msg_release_20200405
```

### 5.2 权限

| 角色 | 权限 |
|------|------|
| SSE、领域 SE、项目经理 | 读写、归并 |
| 开发人员 | 只读；可拉取分支，可 push 个人分支 |

---

## 6. Fix 分支

用于已发布产品的生命周期管理（长期维护与缺陷修复），基于 Release 分支拉取。

### 6.1 命名规范

Fix 分支名**必须以父 Release 分支的分支前缀开头**。

```
{父分支前缀}_fix_{日期}
```

| 字段 | 说明 |
|------|------|
| `{父分支前缀}` | 父 Release 分支去掉末尾日期 |
| `{日期}` | 分支创建日期 `YYYYMMDD` |

**示例：**

```
br_v4.10_develop_msg_release_fix_XX故障_20200405
br_v4.10_develop_msg_release_fix_p370_20200405
```

### 6.2 权限

| 角色 | 权限 |
|------|------|
| SSE、领域 SE、项目经理 | 读写、归并 |
| 开发人员 | 只读；可拉取分支，可 push 个人分支 |

---

## 7. 个人开发分支

日常开发均基于个人分支进行。个人分支从 Develop 或 Release 分支拉取，调测完毕后再合入对应分支。

> **注意：** 个人分支名中**必须**包含 `personal` 关键字，以便自动化工具过滤。

**合入规则：**

- **领域 SE / 项目经理** 的个人分支：由本人直接合入。
- **普通开发人员** 的个人分支：push 至远端仓库后，由分管领域 SE 审核合入。

### 7.1 命名规范

#### BUG 修订

```
{父分支前缀}_personal_{姓名}_bugfix_{日期}
```

**示例：**

```
br_v4.10_develop_msg_personal_yuhui_bugfix_20200405
br_v4.10_develop_msg_release_personal_yuhui_bugfix_20200405
```

#### 功能调测（仅基于 Develop /release分支）

```
{Develop前缀}_personal_{姓名}_{模块名}_{日期}
```

**示例：**

```
br_v4.10_develop_msg_personal_yuhui_route_20200405
```

#### 特性与需求开发

采用 **Feature 分支**（见第 4 节），不使用个人分支。

### 7.2 清理策略

个人分支在合入目标分支后，应于 **2 周内删除**。每季度由领域 SE 统一清理超过 **30 天无提交** 的个人分支。

### 7.3 权限

| 角色 | 权限 |
|------|------|
| 所有开发人员 | 读写（自主管理个人分支） |

---

## 8. 命名规则速查

| 分支类型    | 命名模板                                   |
| ------- | -------------------------------------- |
| Develop | `br_{版本}_develop_{用途}_{日期}`            |
| Feature | `{Develop前缀}_feature_{特性名}_{日期}`       |
| Release | `{Develop前缀}_release_{版本标记}_{日期}`      |
| Fix     | `{父分支前缀}_fix_{日期}`                     |
| 个人（BUG） | `{父分支前缀}_personal_{姓名}_bugfix_{日期}`    |
| 个人（功能）  | `{Develop前缀}_personal_{姓名}_{模块名}_{日期}` |

**通用约定：**

- 各字段之间使用下划线 `_` 连接，字段内不含空格。
- 日期格式统一为 `YYYYMMDD`（如 `20200405`）。
- 用途字段为产品/项目标识，基线产品可省略。
- **分支前缀** = 父分支名去掉末尾 `_YYYYMMDD`，所有后代分支名必须以其开头。
- 严禁在非 Personal 分支名中使用个人姓名或昵称。

## 9. 需求追溯与生命周期管理

### 9.1 分支生命周期状态

每个非 Personal 分支在其生命周期中处于以下状态之一：

```
创建 ──→ [开发中] ──→ [待合入] ──→ [已合入] ──→ 🗑 删除
                   ↘
                  [已废弃] ──→ 🗑 删除
```

| 状态 | 标识 | 判断标准 |
|------|------|---------|
| **开发中** 🟡 | `active` | 分支有近期提交（< 30 天），未提出 MR |
| **待合入** 🔵 | `pending-merge` | 已提出 MR 或领先 develop 有未合入提交 |
| **已合入** ✅ | `merged` | `git branch --merged develop` 包含此分支 |
| **已废弃** 💤 | `abandoned` | 超过 **180 天**无任何提交，且无未合入的独有 commit |

> **建议：** 使用 `git notes` 在分支首个 commit 上标记状态变更：
> ```bash
> git notes add -m "状态: 待合入 | MR: !456 | 审核人: zhangsan" HEAD
> ```

### 9.2 定期巡检策略

| 频率 | 执行人 | 检查内容 |
|------|-------|---------|
| **每周** | 领域 SE | 对自己管辖的 Develop 运行 [[AIRepo/scripts/git-branch-family.sh\|分支家族树工具]]，识别 `🔴 高风险` 分支 |
| **每月** | 领域 SE | 检查 `🟣 已落后` 分支，确认是否可删除 |
| **每季度** | 项目经理 | 全量分支清理：删除 `✅ 已合入` 分支 + `💤 已废弃` 分支 |

## 10. 分支家族树工具

### 10.1 概述

`git-branch-family.sh` 是基于本规范「分支前缀」约定开发的自动化分析工具。

**输入：** 仓库路径 + 一个 Develop 分支名  
**输出：** 该 Develop 所有后代分支的家族树图谱、合并状态、清理建议

### 10.2 使用方式

```bash
# 文本模式（终端快速诊断）
./AIRepo/scripts/git-branch-family.sh <仓库路径> <develop分支名> --text

# 图谱模式（贴入 Obsidian 渲染为可视化流程图）
./AIRepo/scripts/git-branch-family.sh <仓库路径> <develop分支名> --mermaid
```

### 10.3 图谱说明

图谱按颜色编码分支的合并状态：

| 颜色 | 状态 | 含义 | 建议动作 |
|------|------|------|---------|
| 🟠 橙 | 根节点 | Develop 基准分支 | — |
| 🟢 绿 | merged | 已完全合入 develop | `git branch -d` 删除 |
| 🔵 蓝 | clean | 有领先提交，可尝试合并 | 提 MR 合入 |
| 🔴 红 | conflict | 严重落后（>200 commits） | rebase 到最新 develop 后再合 |
| ⚪ 灰 | stale | >180 天无提交 | 确认需求有效性后决定去留 |

详细使用说明见 [[分支家族树图谱案例]]。
