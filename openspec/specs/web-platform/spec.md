# web-platform Specification

## Purpose
Branch Sync Agent V2 的 Web 分支维护工作台：维护人员通过浏览器登录，集中查看、审阅、决策并执行分支同步与推送操作。平台是独立进程，与 V1 Agent 解耦，读经投影、写经 CLI，是 V1 能力的操作入口而非替代品。

## Requirements

### Requirement: 认证与会话

平台提供用户认证与会话管理，未登录不可访问。

#### Scenario: 用户登录访问

- **当** 用户访问平台任何页面
- **则** 未登录被重定向到登录页，登录后方可访问
- **且** 会话保持（过期时间与闲置超时可配置，默认 8 小时 + 闲置自动失效）
- **且** 会话 cookie 使用 HttpOnly + Secure + SameSite=Lax
- **且** 支持退出登录并清除会话

#### Scenario: 登录防护

- **当** 用户提交登录凭据
- **则** 表单 POST 必须带 CSRF token，校验失败拒绝
- **且** 登录路径受 nginx 限速（防爆破）
- **且** 密码等敏感信息不得出现在日志中

### Requirement: 认证后端可替换

认证实现可替换，公司 LDAP/SSO 就绪后切换不改变其余逻辑。

#### Scenario: 切换认证后端

- **当** 公司统一认证（LDAP/SSO）就绪
- **则** 替换认证后端实现，其余页面、授权、会话逻辑不变
- **且** 初版使用环境变量静态配置的账号（`BSA_USERS`：用户名/密码哈希/角色），账号变更需重启生效

### Requirement: 角色与授权

平台区分查看者与操作者两个角色，操作权限按角色校验。

#### Scenario: 角色权限隔离

- **当** 用户登录后访问功能
- **则** 查看者仅可查看（报告/详情/历史/实时状态），不可触发任何操作
- **且** 操作者可执行：触发同步、重跑、改判定、确认继续、放弃、推送
- **且** 每个端点在服务端校验角色（不得仅依赖前端隐藏按钮）
- **且** 角色来自账号配置（初版 env 静态，LDAP 后映射组）

### Requirement: 实时工作台首页

首页展示当前周期实时可操作状态，而非静态报告。

#### Scenario: 工作台待办与总览

- **当** 用户进入首页
- **则** 展示待办区：可推送列表（当前周期 SUCCESS）、ManualReview 待确认、失败/停批重跑入口
- **且** 展示当前周期各目标分支实时状态徽章（可手动/自动刷新）
- **且** 展示快速操作入口（触发同步、重跑）与历史报告入口
- **且** 展示 Agent 运行状态（V1 周期运行中/失败醒目标记）
- **且** 运行中周期仅显示"进行中"徽章，不展示未完成周期的详情

#### Scenario: 页面状态实时性

- **当** 用户长时间停留后操作
- **则** 每次请求从 V1 投影读取最新状态，不缓存过期数据

### Requirement: 历史报告与详情查看

平台提供按日期查看历史报告与 commit/分支详情的能力。

#### Scenario: 历史报告查看

- **当** 用户查看历史报告
- **则** 按日期列出已完成周期报告，三区块视图（Action Required / 已成功同步 / 检测信息）
- **且** 支持按结论筛选（NeedSync/AlreadyIncluded/ManualReview/OutOfScope/失败/停批）

#### Scenario: 详情展开

- **当** 用户展开某 commit/分支详情
- **则** 可查看 patch、diff、编译日志、Agent 修复记录、冲突解决记录
- **且** 详情独立路由页面，patch/编译日志按需加载（满足首页 <3 秒、10 用户并发）

### Requirement: 手动触发同步与重跑

平台支持异步触发同步与重跑，进度可查询。

#### Scenario: 触发同步

- **当** 操作者选择源分支+目标分支触发同步
- **则** 平台经 V1 CLI 异步执行（检测→重判结论→同步 NeedSync）
- **且** 兼容指定 commit SHA 直同步（跳过决策，仍走五道闸门）
- **且** 任务状态机 queued→running→succeeded/failed，失败含错误信息，可重试

#### Scenario: 排队与并发

- **当** V1 周期运行中用户触发同步/重跑
- **则** 任务进入 queued 状态并显示"排队中（等待当前周期完成）"
- **且** 同一目标分支已有运行/排队任务时拒绝重复触发
- **且** 全局 flock 串行化所有 V1 执行，等待超时后任务失败并提示重试

#### Scenario: 重跑

- **当** 操作者对失败/停批分支重跑
- **则** 默认沿用当前活 worktree 按 git 状态重入，全量 build 验证后更新 patch
- **且** 支持 `--fresh` 重建现场并先重判结论（若已合入/超范围则停止提示）
- **且** 超期分支仅可只读查看与重新同步，不提供续做/推送入口

### Requirement: 人工项处理

平台提供失败现场查看与人工决策能力。

#### Scenario: 查看失败现场

- **当** 存在停批/失败分支
- **则** 展示冲突现场、编译错误、Agent 修复记录（来自投影与日志文件）
- **且** 人工处理由用户在 worktree 侧自行完成，平台不提供文件编辑

#### Scenario: 改判定

- **当** 操作者修改某 commit 的 is_bug_fix / risk 判定
- **则** 平台经 V1 CLI 写入 judgments.json（人工覆盖优先）
- **且** 生效于下一次决策执行（cron 周期或重跑重判），不追溯改写已冻结的 decisions.json
- **且** 提供"立即重跑"入口让新判定尽快生效
- **且** 改判定行为记录操作日志（操作人/时间/sha/新值）

#### Scenario: 确认继续与放弃

- **当** 操作者确认某 ManualReview 项允许同步
- **则** 复用直同步路径（指定 sha 强制同步）执行
- **且** 操作者可放弃某 commit/分支，标记并记录操作日志

### Requirement: 推送操作

平台仅在满足硬性前置条件下允许操作者触发推送，且推送必须留痕。

#### Scenario: 推送前置条件

- **当** 操作者点推送
- **则** 平台校验四道闸，任一不过则拒绝并显示原因：
  1. 分支状态为 SUCCESS（全部 cherry-pick + 全部 required_models 编译通过）
  2. worktree 存在
  3. 目标分支不在 safety_rules 的 forbidden_branches
  4. git status --porcelain 干净
- **且** 仅当前周期活 worktree 可推送；超期分支无推送入口

#### Scenario: 推送执行

- **当** 四道闸通过且操作者二次确认（确认框展示目标分支、commit 范围、patch 摘要）
- **则** 平台在对应 worktree 执行 `git push origin HEAD:<target>`
- **且** 禁止 `--force`（硬约束）；远端非 fast-forward 时 git 拒绝，平台回显"远端已前进，请重新同步"
- **且** 推送结果回显（成功/失败+错误），失败可重试（重试=重新同步）
- **且** 推送记录操作日志（操作人、时间、分支、commit 范围、结果）

#### Scenario: 无自动推送

- **当** 平台运行
- **则** 平台无任何自动推送逻辑，推送必须由操作者人工触发并确认
- **且** Agent 侧不新增推送白名单，推送仅存在于平台受限执行器

### Requirement: 操作日志与审计

平台记录敏感操作，审计数据永久保留。

#### Scenario: 操作留痕

- **当** 用户执行敏感操作（登录/登出、触发同步、重跑、改判定、确认继续、放弃、推送）
- **则** 记录操作人、时间、对象（cycle_id/target/sha）、操作类型、结果
- **且** 推送记录含 commit 范围（闸门 4 事后审核 + 闸门 5 审计）
- **且** 审计数据与 V1 数据通过共享标识符（cycle_id/target_branch/sha/文件路径）逻辑关联，渲染时聚合展示

#### Scenario: 审计完整性

- **当** 审计记录写入
- **则** 仅允许追加（应用内无更新/删除入口），文件属主为专用服务账号，操作者无文件级写权限
- **且** 每日备份兜底；不做哈希链/签名链

### Requirement: 数据保留分级

平台数据按级别保留，审计类永久，体积日志限时。

#### Scenario: 数据分级

- **当** 平台与 V1 数据积累
- **则** L1 审计（cycle.json/decisions.json/report.html/audit diff/patch/操作日志）永久保留
- **且** L2 体积日志（build log/run.log）默认保留 30 天可配置，每日清理
- **且** L3 worktree 仅保留当前周期，由 V1 cron 清理
- **且** 清理只删除可再生产物，不触碰审计数据

### Requirement: 备份与恢复

平台与 V1 关键数据每日备份，可恢复。

#### Scenario: 每日备份

- **当** 每日备份任务执行
- **则** 打包平台 DB + V1 state.sqlite3 + judgments.json + cycle.json 为归档
- **且** 同机保留最近 7 份自动滚动，RPO ≤ 1 天
- **且** worktree 与 patch 不纳入备份（可重建/重同步）

#### Scenario: 恢复

- **当** 数据损坏或误删需要恢复
- **则** 还原备份 + 重建环境 + 重跑同步即可恢复，不依赖 worktree

### Requirement: 可观测性与部署

平台提供健康检查与结构化日志，配置走环境变量。

#### Scenario: 健康检查与日志

- **当** 平台运行
- **则** 提供健康检查端点（systemd/nginx 探活）
- **且** 请求日志结构化并接入 logrotate 轮转
- **且** 平台 DB 带 schema_version，结构变更走迁移
- **且** 平台与 Agent 同机独立进程，nginx 反代 + HTTPS 终结，配置全走环境变量

### Requirement: 平台自身数据存储

平台使用独立数据库存储会话、操作日志与异步任务注册表，并关联 V1 数据。

#### Scenario: 平台库与 V1 关联

- **当** 平台读写自身状态
- **则** 会话、操作日志、任务记录存于平台独立 SQLite，不与 V1 state.sqlite3 混用
- **且** 平台记录以 V1 标识符（cycle_id/target/sha/文件路径）关联 V1 数据
- **且** 平台直接读取 V1 数据仅经投影 CLI，写入仅经 V1 CLI 子进程
